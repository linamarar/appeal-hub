## UI-001 — Экран создания обращения визуально не относится к новой дизайн-системе

- **Приоритет:** P2
- **Экран:** Создание обращения
- **Маршрут:** `#/flow`
- **Viewport:** 1440×900 / 1280×800 / 1024×768 / 390×844 (актуально на всех)
- **Окружение:** LOCAL (проверено по коду)
- **Компонент:** вся страница — `.btn`, `.page-header`, `.flow-steps`, `.upload-zone`, `.doc-preview`, `.ai-log`, `.appeal-card`, `.success-banner` (`styles/main.css`)
- **Описание:** Единственный экран, полностью построенный на «legacy»-стилях (`view--legacy`, подключение `styles/main.css`), использующих шрифт Inter и серую палитру (`--gray-*`, `--blue-*`), тогда как все остальные экраны используют токен-based систему `ui-*` со шрифтом `--font-family-primary` (TT Firs) и палитрой из `tokens.css`. При переходе «Обращения → Создать обращение» происходит резкая визуальная смена стиля кнопок, заголовков, карточек.
- **Шаги воспроизведения:** Открыть `#/appeals`, нажать «Создать обращение» (или перейти на `#/flow`).
- **Ожидаемый результат:** Единая визуальная система (шрифт, цвета, кнопки, карточки) с остальным приложением.
- **Фактический результат:** Другой шрифт, другая палитра кнопок (`.btn--primary` тёмно-серый вместо `--color-action-primary`), другой стиль карточек/бейджей/спиннера.
- **Основание:** визуальная целостность, design-токены (`docs/design-tokens.md` §13 прямо фиксирует, что legacy-прототип не мигрирован).
- **Shared impact:** ONE SCREEN (весь экран `#/flow`, но затрагивает много legacy-компонентов сразу).
- **Риск исправления:** HIGH — потребует полной пересборки экрана на `ui-*` компонентах и данных из `AppealsRepository`/`status-catalog.js` (частично пересекается с DEF-008 по hardcoded ID).
- **Затрагиваемые экраны:** только `#/flow`.
- **Предполагаемый модуль:** `index.html` (`#view-flow`), `scripts/app.js` (`renderFlowAppealCard`, `initFlow`, `simulateAIProcessing`), `styles/main.css` — без изменений в рамках этой задачи.
- **Статус:** NEW
- **Возможные варианты для обсуждения:** (а) полный редизайн экрана на `ui-*` компонентах отдельным этапом; (б) осознанно оставить legacy-стиль как временный «демо AI-обработки» экран с явной пометкой; решение не принимается в рамках аудита.

## UI-002 — Нет активного пункта меню при нахождении на экране создания обращения

- **Приоритет:** P3
- **Экран:** Создание обращения
- **Маршрут:** `#/flow`
- **Viewport:** все (не зависит от разрешения)
- **Окружение:** LOCAL (проверено по коду)
- **Компонент:** `shell-nav__item` (сайдбар)
- **Описание:** `switchView()` в `scripts/app.js` использует карту `navActiveMap` с ключами `dashboard/clients/templates/analytics/settings`; для `viewId === 'flow'` ни один пункт меню не входит в соответствующую группу, поэтому активная подсветка снимается со всех пунктов.

- **Ожидаемый результат:** Логично было бы подсвечивать «Обращения» (т.к. создание обращения — часть этого раздела) либо иметь отдельную индикацию.

- **Shared impact:** ONE SCREEN.
- **Риск исправления:** LOW — добавление `flow` в группу `dashboard` в `navActiveMap`.
- **Затрагиваемые экраны:** `#/flow`.
- **Предполагаемый модуль:** `scripts/app.js` (`switchView`, `navActiveMap`) — без изменений в рамках этой задачи.
- **Статус:** FIXED
- **Исправление:** `navActiveMap.dashboard` включает `flow` — на `#/flow` активен пункт «Обращения».

## UI-003 — Несогласованная высота полей и кнопок в одной строке

- **Приоритет:** P3
- **Экран:** Список обращений, Карточка обращения, Карточка клиента
- **Маршрут:** `#/appeals` (toolbar), `#/appeals/:id` (блок действий), `#/clients/:id` (тулбар вкладки «Обращения»)
- **Viewport:** 1440×900 / 1280×800 / 1024×768 (наиболее заметно, когда контролы в одной строке не переносятся)
- **Окружение:** LOCAL (проверено по коду)
- **Компонент:** `ui-input`/`ui-search-input`/`ui-select` (`min-height: 46px`) рядом с `ui-button--md` (`--control-height-md: 40px`) или `ui-button--sm` (`--control-height-sm: 32px`)
- **Описание:** Токены задают `--control-height-md: 40px`, но `.ui-input`/`.ui-search-input`/`.ui-select` используют собственное жёстко заданное `min-height: 46px` (комментарий в `input.css`/`select.css`: «compact toolbar variant»), из-за чего в одной горизонтальной группе высота элементов не совпадает.
- **Шаги воспроизведения:**
  1. `#/appeals` → toolbar: поле поиска и селекты (46px) стоят рядом с кнопкой «Сбросить» (`ui-button--sm`, 32px).
  2. `#/appeals/:id` → блок действий: кнопки «Принять в работу»/«Назначить исполнителя» (40px) стоят в одной строке с `<select>` статуса (46px).
- **Ожидаемый результат:** Единая базовая линия (baseline) высоты интерактивных элементов в одной строке.
- **Фактический результат:** Видимая разница в 6–14px по высоте между соседними контролами.
- **Основание:** design-токены (`docs/design-tokens.md` §9 «Control sizes»), визуальная целостность.
- **Shared impact:** GLOBAL COMPONENT (`ui-input`, `ui-select`, `ui-button` используются на всех экранах с формами/фильтрами).
- **Риск исправления:** MEDIUM — правка затронет размеры полей/кнопок глобально, требует сверки с Figma control heights (L/M/S) перед изменением.
- **Затрагиваемые экраны:** Обращения, Карточка обращения, Клиенты, Карточка клиента, Шаблоны, модалка назначения.
- **Предполагаемый модуль:** `styles/components/input.css`, `styles/components/select.css`, `styles/components/button.css` — без изменений в рамках этой задачи.
- **Статус:** NEW
- **Возможные варианты для обсуждения:** привести все компактные контролы toolbar к единой высоте (40px по токену) либо явно задокументировать «46px — сознательный toolbar-вариант» и подобрать кнопки такой же высоты для этого контекста.

## UI-004 — Нестилизованный `dl`/`dt`/`dd` вместо компонента meta-list на карточке клиента

- **Приоритет:** P2
- **Экран:** Карточка клиента
- **Маршрут:** `#/clients/:id`
- **Viewport:** 1440×900 / 1280×800 / 1024×768 / 390×844 (не зависит от разрешения)
- **Окружение:** LOCAL (проверено по коду)
- **Компонент:** блок «Контактная информация» в сайдбаре (первая карточка)
- **Описание:** `renderSidebar()` в `scripts/pages/client-detail-page.js` генерирует разметку `<dl class="ui-meta-list"><div class="ui-meta-list__row"><dt>…</dt><dd>…</dd></div>…</dl>`, однако `styles/components/meta-list.css` описывает только `.ui-meta-list__item`, `.ui-meta-list__label`, `.ui-meta-list__value` — классы `.ui-meta-list__row` и теги `dt`/`dd` внутри `.ui-meta-list` нигде не стилизуются. В результате блок рендерится дефолтными браузерными стилями `dl` (собственные отступы/интервалы браузера), визуально не совпадая с остальными meta-list блоками в приложении (например, «Параметры обращения» на карточке обращения, использующей корректную разметку `.ui-meta-list__item`).
- **Шаги воспроизведения:** Открыть любую карточку клиента (например, из списка «Клиенты» → «Открыть»), посмотреть на первую карточку сайдбара «Контактная информация».
- **Ожидаемый результат:** Компактные строки «label — значение» с разделителями, как в `.ui-meta-list__item` на карточке обращения.
- **Фактический результат:** Блок с браузерными отступами по умолчанию для `dl`/`dd` (обычно отступ `dd` слева ~40px, увеличенные вертикальные интервалы), визуально «неаккуратный» на фоне соседних карточек сайдбара (`.client-detail__list-item`), которые оформлены компактно.
- **Основание:** визуальная целостность, несоответствие компонента (Figma: `docs/client-card-figma-mapping.md` указывает «Meta list / inline» для stats row, аналогичный паттерн для контактного блока).
- **Shared impact:** ONE SCREEN (проявляется только на карточке клиента; сам компонент `ui-meta-list` в остальных местах используется корректно).
- **Риск исправления:** LOW — точечная правка разметки в одной функции рендера (замена `dl/dt/dd` на существующую структуру `.ui-meta-list__item/__label/__value`), CSS менять не требуется.
- **Затрагиваемые экраны:** `#/clients/:id`.
- **Предполагаемый модуль:** `scripts/pages/client-detail-page.js` (`renderSidebar`) — без изменений в рамках этой задачи.
- **Статус:** FIXED
- **Исправление:** разметка контактов переведена на `ui-meta-list__item` / `__label` / `__value`; глобальный CSS не менялся.

## UI-005 — Модалка назначения исполнителя без `aria-modal`, Escape и управления фокусом

- **Приоритет:** P2
- **Экран:** Карточка обращения
- **Маршрут:** `#/appeals/:id` → кнопка «Назначить исполнителя» / «Переназначить»
- **Viewport:** все (не зависит от разрешения, но особенно критично для клавиатурной навигации на 1440/1280, где вероятнее работа с клавиатурой)
- **Окружение:** LOCAL (проверено по коду)
- **Компонент:** `ui-modal` (`#assign-modal`)
- **Описание:** В `scripts/appeal-detail.js` (`openAssignModal`/`closeAssignModal`/`initModalHandlers`) модалка открывается/закрывается по клику, но:
  1. Отсутствует обработчик `keydown` для клавиши `Escape` (для сравнения — `#filters-drawer` в `scripts/app.js` имеет такой обработчик).
  2. Фокус не переводится на первый интерактивный элемент модалки (`#assign-user-select`) при открытии и не возвращается на кнопку-триггер при закрытии.
  3. Атрибут `aria-modal="true"` не проставлен ни на `#assign-modal`, ни на `#filters-drawer` (есть только `role="dialog"`), из-за чего для скринридеров фоновый контент формально остаётся в дереве доступности как активный.
- **Шаги воспроизведения:** Открыть `#/appeals/:id` любого обращения без исполнителя → нажать «Назначить исполнителя» с клавиатуры (Tab/Enter) → попытаться закрыть модалку клавишей `Escape`.
- **Ожидаемый результат:** Escape закрывает модалку; фокус после открытия — на первом поле формы; после закрытия — возвращается на кнопку-триггер; `aria-modal="true"` присутствует.
- **Фактический результат:** Escape не работает; фокус остаётся там, где был до открытия (обычно на кнопке-триггере, которая визуально теперь скрыта за модалкой); `aria-modal` отсутствует.
- **Основание:** accessibility (клавиатурная навигация, ARIA-паттерн модальных диалогов).
- **Shared impact:** GLOBAL COMPONENT (в приложении один компонент модалки — `ui-modal`; при добавлении новых модалок проблема размножится).
- **Риск исправления:** MEDIUM — требует добавления focus trap / return-focus логики и обработчика Escape по аналогии с уже существующей реализацией в `#filters-drawer`.
- **Затрагиваемые экраны:** `#/appeals/:id` (единственное место использования модалки сейчас).
- **Предполагаемый модуль:** `scripts/appeal-detail.js` (`openAssignModal`, `closeAssignModal`, `initModalHandlers`), `index.html` (`#assign-modal`, `#filters-drawer` — атрибут `aria-modal`) — без изменений в рамках этой задачи.
- **Статус:** NEW

## UI-006 — Индикатор уведомлений всегда включён независимо от реального состояния

- **Приоритет:** P2
- **Экран:** Application shell (все экраны, где виден header)
- **Маршрут:** любой (индикатор в header, вне `.view`)
- **Viewport:** 1440×900 / 1280×800 / 1024×768 (на 390×844 профиль/уведомления видны, `shell-header__profile-name` скрыт, но иконка с точкой остаётся)
- **Окружение:** LOCAL (проверено по коду)
- **Компонент:** `.shell-header__badge-dot`
- **Описание:** В `index.html` элемент `<span class="shell-header__badge-dot" aria-hidden="true">` рендерится статически, без условия на наличие непрочитанных уведомлений; кнопка уведомлений не имеет обработчика клика (известный отдельный функциональный дефект, не дублируется). Совместно эти два факта создают устойчиво вводящее в заблуждение состояние: пользователь весь сеанс видит «есть непрочитанные уведомления», но нажатие ничего не делает и точка никогда не исчезает.
- **Шаги воспроизведения:** Открыть любой экран приложения, посмотреть на иконку колокольчика в header.
- **Ожидаемый результат:** Индикатор отображается только когда есть реальные непрочитанные уведомления, и пропадает после просмотра.
- **Фактический результат:** Индикатор отображается всегда, вне зависимости от каких-либо данных.
- **Основание:** usability («состояние вводит в заблуждение» — явный критерий P2 в ТЗ).
- **Shared impact:** GLOBAL COMPONENT (header виден на всех экранах).
- **Риск исправления:** LOW (визуально) — скрыть точку по умолчанию до появления реальной модели уведомлений; полноценная реализация уведомлений — отдельная задача продукта.
- **Затрагиваемые экраны:** все.
- **Предполагаемый модуль:** `index.html` (`.shell-header__notifications`), `styles/layout/shell.css` (`.shell-header__badge-dot`) — без изменений в рамках этой задачи.
- **Статус:** FIXED
- **Исправление:** `.shell-header__badge-dot` удалён из разметки header; кнопка-колокольчик остаётся как заглушка.

## UI-007 — Разный UX-паттерн мобильных фильтров между списками

- **Приоритет:** P3
- **Экран:** Клиенты, Шаблоны (в сравнении с Обращениями)
- **Маршрут:** `#/clients`, `#/templates` vs `#/appeals`
- **Viewport:** 1024×768 и 390×844 (где различие проявляется)
- **Окружение:** LOCAL (проверено по коду)
- **Компонент:** toolbar фильтров (`.appeals-toolbar` vs `.ui-page__toolbar`)
- **Описание:** На «Обращениях» при ширине ≤768px инлайн-фильтры скрываются (`.appeals-toolbar__inline-filters { display: none }`), появляется кнопка «Фильтры», открывающая `#filters-drawer` (полноценная выезжающая панель). На «Клиентах» и «Шаблонах» (`styles/components/page-layout.css`, `.ui-page__toolbar-row { flex-wrap: wrap }`) выделенного мобильного брейкпоинта и drawer нет — селекты и поиск просто переносятся на новую строку внутри той же тулбар-строки.
- **Шаги воспроизведения:** Сравнить `#/appeals` и `#/clients` на ширине ≤1024px / 390px.
- **Ожидаемый результат:** Единый паттерн взаимодействия с фильтрами на всех списковых экранах.
- **Фактический результат:** Два разных паттерна: drawer (Обращения) vs построчный перенос (Клиенты/Шаблоны).
- **Основание:** визуальная целостность, usability (согласованность паттернов между похожими экранами).
- **Shared impact:** MULTIPLE SCREENS (Клиенты, Шаблоны — в сравнении с Обращениями).
- **Риск исправления:** MEDIUM — требует решения, какой паттерн считать целевым, и синхронной правки toolbar на затронутых экранах.

## UI-009 — Таблицы требуют горизонтального скролла на ≤1024/390px

- **Шаги воспроизведения:** Открыть `#/appeals` (или любой другой список) на ширине 390px — по коду видно, что колонки «SLA», «Обновлено» и кнопка «Открыть» окажутся за пределами видимой области без скролла.
- **Ожидаемый результат:** Для целевого мобильного разрешения (390px) — читаемое представление без необходимости горизонтального скролла (например, карточный вид строк) либо осознанно принятое решение оставить горизонтальный скролл как admin-паттерн.
- **Фактический результат:** Горизонтальный скролл обязателен на 1024 и 390px для всех таблиц приложения.
- **Основание:** usability, адаптивность (проверено по коду, не воспроизведено визуально в браузере).
- **Shared impact:** GLOBAL COMPONENT (`ui-data-table` используется на 5 экранах).
- **Риск исправления:** MEDIUM — правка одного компонента затронет все таблицы; полноценная альтернатива (карточный список на мобильном) — более высокий риск и объём работ.
- **Затрагиваемые экраны:** `#/appeals`, `#/clients`, `#/templates`, `#/clients/:id`, `#/analytics`.
- **Предполагаемый модуль:** `styles/components/table.css` — без изменений в рамках этой задачи.
- **Статус:** NEW
- **Возможные варианты для обсуждения:** признать горизонтальный скролл осознанным admin-паттерном для мобильных (многие B2B-панели так делают) — тогда это не требует правок, только явного продуктового решения.
